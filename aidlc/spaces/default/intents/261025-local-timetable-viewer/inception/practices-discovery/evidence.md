## Interview decisions

1. Where new work lands. The human wrote: "create a new branch for this work, and squash merge at the end". Read as a new short-lived branch for this service, squash-merged to `main` at the end. This work does not stay on `athena-timetable-lake`. Older milestone branches stay history.
2. Thin slice. The human chose A: build a thin running slice first: the existing database, one view, and enough of a screen to see it. That replaces the lake sentence that skipped a running slice. The classic scope still does not run a separate skeleton checkpoint. The order of work is the thin slice first.
3. Tests. The human chose A: the new reader gets tests now: unit tests plus a thin check of the three views (all trains today, trains that deviate, and a chosen pair of stations). The bar is that its own suite stays green. No 80% gate until continuous integration exists. Screen tests were written as waiting until a UI toolkit is chosen. The same interview chose TypeScript for the screen, so screen tests are in scope once that TypeScript UI exists, on that stack, and do not wait on an unnamed toolkit. Live-sched tests run only when that package changes. Reader tests must not change the SQLite file. Methodology stays test-after. Ordering stays: Implement each applicable testable layer, then write and run that layer's tests.
4. Where it runs. The human chose A: local Docker only. Do not create `dev`, `staging`, or `prod` for this service. Do not add cloud controls.
5. Checks. The human chose C: add local secret scanning, dependency checks, and a dynamic check of the local reader now, without standing up continuous integration. No formatter was requested, so this pass does not add one and does not ban one. The new code is TypeScript, so the scanners are not Python-only.
6. Where the code lives. The human wrote: "typescript / FP (where possible) fro backend, FE is also typescript. This will be used fro the long term, but there will be other apps within this mono repo. place this code in ./apps/local-timetable/<db/server/fe>". "fro" is read as "for". The layout is `apps/local-timetable/db`, `apps/local-timetable/server`, and `apps/local-timetable/fe`. Backend and frontend are TypeScript. Functional style is preferred where possible. This monorepo will hold other apps later. The reader stays outside live-sched, does not import `schedule_poc`, does not create or rewrite the SQLite file, and fails the request if the file is missing, deleted, locked, or an older schema. The three views are answered by this server, not by `list_journeys()`. `service_guid` and the other store names stay. The Python live-sched package remains the writer of that SQLite file and stays outside `apps/`. TypeScript identifiers around the store tokens use camelCase, the idiom for that language. The human did not spell a separate case rule. `service_guid` and the other store names keep their existing spelling.
